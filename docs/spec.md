# Спецификация приложения «Календарь звонков»

## Обзор

«Календарь звонков» — упрощённый сервис бронирования времени по мотивам Cal.com. Владелец создаёт типы событий (название, описание, длительность), гость выбирает тип, видит свободные слоты и бронирует встречу. Владелец видит все предстоящие встречи в одном списке.

Архитектура — full-stack: фронтенд (React + Vite + Mantine) и бэкенд (Fastify + SQLite). API описывается TypeSpec-контрактом, из которого генерируются OpenAPI, клиентский SDK (orval) и серверные артефакты (`@typespec/json-schema` → Fastify). Фронтенд обращается к API только через сгенерированный SDK.

## Доменная модель

См. `GLOSSARY.md`. Ключевые сущности:

- **Тип события** — `{ id, name, description, duration }` (duration в минутах).
- **Встреча** — единица бронирования переменной длительности, заданной типом события.
- **Слот** — интервал длительностью типа события, сетка 30 минут, горизонт 14 дней.
- **Бронь** — `{ id, name, email, typeId, slotStart, slotEnd, createdAt }`.
- **Расписание** — ежедневно 09:00–18:00.

## Пользовательские истории

### Владелец

- **US-1. Создание типа события.** Как владелец, я хочу создать тип события (название, описание, длительность), чтобы гость мог бронировать встречи этого типа.
- **US-2. Просмотр предстоящих встреч.** Как владелец, я хочу видеть список предстоящих встреч всех типов, чтобы знать, кто и когда записался.

### Гость

- **US-3. Просмотр типов событий.** Как гость, я хочу видеть список типов событий (название, описание, длительность), чтобы выбрать подходящий.
- **US-4. Выбор типа и просмотр слотов.** Как гость, я хочу выбрать тип и увидеть свободные слоты на ближайшие 14 дней, чтобы выбрать удобное время.
- **US-5. Бронирование слота.** Как гость, я хочу забронировать свободный слот (указав имя и email), чтобы записаться на встречу.
- **US-6. Подтверждение брони.** Как гость, я хочу видеть подтверждение после бронирования, чтобы убедиться, что запись прошла.

## Критерии приёмки

### US-1. Создание типа события

- **AC-1.1.** На странице `/types/new` есть форма с полями «Название», «Описание», «Длительность (минуты)».
- **AC-1.2.** «Название» обязательно, непустое.
- **AC-1.3.** «Длительность» обязательна, положительное целое число минут.
- **AC-1.4.** «Описание» необязательно.
- **AC-1.5.** После отправки тип создаётся и появляется в списке типов.

### US-2. Просмотр предстоящих встреч

- **AC-2.1.** На странице `/bookings` показан список всех броней всех типов.
- **AC-2.2.** Каждая бронь показывает имя, email, тип события, время слота и время создания.
- **AC-2.3.** Пустой список показывает состояние «нет встреч».

### US-3. Просмотр типов событий

- **AC-3.1.** На лендинге `/` показан список типов событий.
- **AC-3.2.** Каждый тип показывает название, описание и длительность.

### US-4. Выбор типа и просмотр слотов

- **AC-4.1.** Выбор типа ведёт на `/booking/:typeId`.
- **AC-4.2.** Календарь показывает слоты на 14 дней от текущей даты.
- **AC-4.3.** Слоты начинаются каждые 30 минут, длительность = длительность типа.
- **AC-4.4.** Занятые слоты показаны как «Занято» и не выбираются.
- **AC-4.5.** Прошедшие слоты не показываются.

### US-5. Бронирование слота

- **AC-5.1.** Гость выбирает свободный слот и вводит имя и email.
- **AC-5.2.** Имя обязательно, непустое.
- **AC-5.3.** Email обязателен, валидный формат.
- **AC-5.4.** После бронирования слот становится занятым.
- **AC-5.5.** Повторная запись на пересекающееся время не проходит, в том числе для другого типа события.

### US-6. Подтверждение брони

- **AC-6.1.** После успешной брони гость видит «Бронь подтверждена» с датой и временем.

## Правила бронирования

- **Занятость.** Две брони конфликтуют, если их интервалы `[slotStart, slotEnd)` пересекаются, независимо от типа события.
- **Проверка на сервере.** Правило занятости выполняется на сервере; прямой запрос в API не может создать вторую запись на пересекающееся время.
- **Сетка.** Слоты начинаются в точках сетки каждые 30 минут (09:00, 09:30, …), длительность = длительность типа.
- **Горизонт.** Слоты формируются на 14 дней от текущей даты.
- **Расписание.** Ежедневно 09:00–18:00.

## API-контракт

| Метод | Путь | Описание | Ответ |
|---|---|---|---|
| GET | `/event-types` | Список типов событий | 200 `[{ id, name, description, duration }]` |
| POST | `/event-types` | Создать тип | 201 `{ id, name, description, duration }` |
| GET | `/slots?typeId&from&to` | Слоты типа со статусами | 200 `[{ start, end, status }]` |
| POST | `/bookings` | Создать бронь | 201 `{ id, name, email, typeId, slotStart, slotEnd, createdAt }` / 409 |
| GET | `/bookings` | Список броней | 200 `[{ id, name, email, typeId, slotStart, slotEnd, createdAt }]` |

Тела запросов:

- `POST /event-types`: `{ name, description, duration }`.
- `POST /bookings`: `{ name, email, typeId, slotStart }`.

## Решения по тестированию

- **Юнит-тесты (Vitest).** Генерация слотов (сетка 30 мин, длительность типа, горизонт 14 дней, только будущие) и проверка занятости (пересечение интервалов).
- **Интеграционные тесты (API).** Эндпоинты: создание типа, список слотов со статусами, создание брони (201), конфликт (409), список броней.
- **E2E (Playwright).** Основной сценарий: гость выбирает тип, открывает календарь, бронирует свободный слот, видит подтверждение; владелец видит встречу в списке. Плюс сценарий конфликта: занятый слот не предлагается, повторная запись не проходит.
